# 코드 리뷰 가이드

> PR 단위로 진행하는 코드 리뷰 절차. {{REVIEW_TARGET_PRS}} PR이 대상.
> AI에게 리뷰를 위임할 때는 이 문서의 분류 기준(§2)과 리포트 양식(§4)을 함께 전달한다.

---

## 1. 목적과 적용 시점

### 목적
- 머지 전 결함 식별
- AI 산출물에 사용자 검증 트레일 남기기
- 보류 판정한 항목을 후속 추적 가능한 상태로 분리

### 적용 시점
PR 생성 후 머지 전. 위 인용문에 적힌 홉이 전부 대상이다.

### 스킵 조건
다음 경우에는 리뷰를 생략할 수 있다. 스킵 사유는 PR 코멘트에 명시한다.

- 5줄 이내 수정
- 문서만 변경 (코드 영향 0)
- 자동 생성 파일만 변경 (lockfile, 자동 생성 라우트·타입 등)
- 의존성 버전만 변경 (코드 변경 없음)

스킵 여부가 모호하면 리뷰를 진행한다.

---

## 2. 분류 체계

발견 사항은 4단계로 분류한다. 잘된 점은 별도 섹션(Positive)으로 기록한다.

| 단계 | 의미 | 머지 처리 |
|---|---|---|
| Critical | 동작 결함 · 보안 결함 · 데이터 손실 위험 | 반드시 수정 후 머지 |
| Major | 강력 권장 사항 (구조 결함, 명확한 안티 패턴) | 수정 또는 근거 있는 기각 |
| Minor | 선택 사항 (개선 여지, 트레이드오프 영역) | 보류 가능 |
| Note | 정보성 메모 (배경 설명, 후속 작업 힌트) | 처리 불요 |
| Positive | 잘 작성된 패턴 (학습 자료로 보존) | 처리 불요 |

### 분류 기준

**Critical**
- 실제 결함이 발화하는 시나리오 존재
- 보안 · 데이터 무결성에 직접 위험
- 머지 후 즉시 발견될 가능성 높음

**Major**
- 기능 동작은 하지만 구조 · 패턴 측면에서 명확한 결함
- 다음 작업에서 빚으로 누적될 가능성 높음
- 트레이드오프가 의도된 경우는 Minor로 강등

**Minor**
- 개선 여지가 있지만 현재 동작에는 영향 없음
- 의도된 트레이드오프
- 시간 · 우선순위 측면에서 보류 가능

**Note**
- 발견 사항이라기보다 배경 설명
- 후속 작업의 진입점 표시

## 3. 리뷰 절차

```
1. PR diff 전체 훑기
2. 변경 파일별 점검
3. 발견 사항을 4단계로 분류
4. 리포트 작성 (양식은 §4)
5. 사용자 판정 (수용 / 기각 / 보류)
6. Critical · Major 처리 후 머지
```

### 점검 영역

- 타입 안전성 (any 사용, 타입 가드, API 응답 타입 정합)
- 에러 처리 (예외 경로, 사용자 노출 메시지, 401/403 등 상태 코드 처리)
- 명명 일관성 (변수 · 함수 · 컴포넌트 명명 규칙)
- 패턴 일관성 (프로젝트 기존 코드의 관용 패턴 준수)
- 데이터 필드 정합 (필드 변경 시 참조 지점도 함께 갱신됐는지)
- 디자인 토큰 정합 (색 · radius · 타이포를 토큰으로 사용했는지, 하드코딩 색 금지)
- 사용 안 하는 코드 (dead code, 임포트, 변수)
- 주석 · 문서 정합 (코드 변경에 따른 문서 동기화)
- 검증 명령 통과 여부 ({{VERIFY_COMMANDS_INLINE}})

## 4. 리포트 양식

PR 코멘트에 작성한다. 파일 사본이 필요하면 `.claude/local/reviews/{브랜치명}.md` (이그노어 대상. 폴더는 첫 리뷰 때 만든다).

```markdown
# Code Review — {PR 제목 또는 브랜치명}

## 범위
- PR: `feature/xxx` → `{{INTEGRATION_BRANCH}}`
- 커밋: {커밋 해시 또는 요약}
- diff 요약: N files changed, +N / -N

## 검증 상태
{{VERIFY_CHECK_LINES}}
- 수동 동작 확인 — 완료 / 보류

## 발견 사항

### Critical (반드시 수정)
{없으면 "없음."}

### Major (강력 권장)
{없으면 "없음."}

**M1. {제목}** [영역 태그]
- 현재 상태:
- 문제:
- 대안:

### Minor (선택)
**m1. {제목}** [영역 태그]
- 현재 상태:
- 개선 여지:
- 트레이드오프:

### Note (정보성)
- {배경 설명 또는 후속 작업 힌트}

### Positive (잘된 점)
**P1. {제목}**
- {왜 잘 작성됐는지}

## 남겨둔 이슈
- {보류 판정 항목 요약 + 후속 처리 계획}

## 최종 판정
- 수용:
- 기각:
- 보류:
```

### 양식 사용 규칙

- Critical · Major는 대문자 `M1, M2`로 식별. Minor는 소문자 `m1, m2`
- 각 항목에 영역 태그를 붙임 (예: `[타입]`, `[구조]`, `[토큰]`, `[문서 sync]`)
- 대안 제시는 "대안이 항상 정답은 아님" 단서를 포함 — 트레이드오프 영역에서 단일 정답을 강요하지 않음
- Positive 섹션은 학습 자료. 단순 칭찬이 아니라 "왜 잘됐는지" 분석 포함

## 5. 사용자 판정

리뷰 항목 각각에 대해 다음 세 가지 중 하나로 판정한다.

| 판정 | 의미 |
|---|---|
| 수용 | 본 PR에서 즉시 처리 |
| 기각 | 처리 안 함. 기각 근거 명시 필수 |
| 보류 | 본 PR 밖에서 후속 처리. 후속 처리 경로 명시 필수 |

### 판정의 의미

판정은 AI의 발견을 사람이 검토한 흔적이다. AI가 발견한 잠재 이슈를 시간 · 우선순위 기반으로 의도적으로 분리하는 결정 자체가 협업 트레일의 일부다.

자동 수용도, 자동 기각도 권장하지 않는다. 항목별 판정을 명시한다.

### 기각 근거 예시

- 트레이드오프 영역의 의도된 결정 (현재 구조가 충분)
- 외부 제약(라이브러리 동작 · 환경 한계)으로 처리 불가
- 평가 기준 · 우선순위 측면에서 다른 작업 대비 후순위

### 보류 항목 후속 처리

- `docs/log/decision-backlog.md`에 등록
- 사이클 회고의 "다음 사이클 메모" 섹션 후보로 분리
- 후속 PR 제목에 명시 (예: `fix: 코드 리뷰 m1 처리`)

## 6. 리뷰 도구의 운용

AI에게 리뷰를 위임할 때 다음을 명시한다.

- 4단계 분류 기준 (§2)
- 리포트 양식 (§4)
- 점검 영역 (§3)
- 출력 위치 (PR 코멘트)

AI 리뷰는 사람 판정을 대체하지 않는다. AI가 분류한 결과에 대해 사람이 재분류할 수 있다.

### AI 리뷰의 한계

- 외부 레퍼런스 UX 패턴 인지 약함 (디자인 레퍼런스 정합, 도메인 컨벤션)
- 잠복 버그 발견은 명시적 시연 또는 라이브러리 소스 직접 확인이 더 강함
- "그럴듯한 답변" 만들기 관성 — 1차 자료 인용 압박이 없으면 추측 답변 가능

→ AI 리뷰만으로 머지 결정하지 않고, 시연 · 테스트 · 1차 자료 대조와 병행한다.

## 7. 후속 추적

보류 · 기각 항목은 다음 위치 중 하나에 기록되어 있어야 한다.

- `docs/log/decision-backlog.md`
- 사이클 회고의 "다음 사이클 메모" 섹션

후속 추적 경로가 없는 보류는 누락된다. 보류 판정 시 추적 경로를 함께 명시한다.
