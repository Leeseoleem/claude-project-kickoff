# 디자인 토큰 2층 정리

색을 원시 토큰과 기능 토큰으로 나누고, 다크모드 값을 도출하고, 대비를 검사한다.

**먼저 읽는다: `${CLAUDE_PLUGIN_ROOT}/skills/tokens/references/naming.md`**
두 네이밍 체계의 정의, 어느 쪽을 쓸지 정하는 감지 규칙, 다크모드 도출 규칙이 전부 거기 있다. 이 파일을 읽기 전에는 토큰 이름을 짓지 않는다.

**보조 스크립트: `${CLAUDE_PLUGIN_ROOT}/skills/tokens/scripts/tokens.py`**
표준 라이브러리만 쓴다. `python3 tokens.py` 로 사용법이 나온다.

```
scan <경로...>              하드코딩된 색·radius·spacing 수집. 문서(.md)는 따로 모은다
contrast <fg> <bg> [기준]   대비비 하나. 기준은 text(4.5) | ui(3.0) | large(3.0)
check <json파일> [--md]     쌍 일괄 검사. 쌍마다 기준 선언 가능. --md면 마크다운 표
scale <hex> [이름] [단계]   기준색을 그 단계에 두고 50~950 생성 (기본 500)
fill <json파일> [이름]      확정된 단계는 보존하고 빈 단계만 생성
audit <json파일> [--same-family]  사실상 중복인 색 찾기
```

**절대 규칙 세 개**

1. 색 값을 눈대중으로 만들지 않는다. 스케일 생성과 대비 판정은 반드시 스크립트를 돌린다.
2. 하드코딩된 색을 자동으로 치환하지 않는다. 리포트만 내고 사람이 승인한다.
3. 대비 미달을 조용히 넘기지 않는다. 조정하거나, 못 하면 그 사실을 문서에 남긴다.

## STEP 1. 입력 확보

아래 순서로 찾는다. 위에서 찾으면 아래는 건너뛴다.

1. **이미 정의된 토큰** — `tailwind.config.*`, CSS의 `@theme` 또는 `:root` 변수 블록, `theme/*.ts`, `tokens*.json`, `*.tokens.json` (Tokens Studio 형식)
2. **사용자가 주는 파일** — 없으면 요청한다. 이렇게 묻는다.

   > 원시 색이 정의된 파일이 있으면 올려줘. CSS 변수 블록, `tailwind.config.js`, Tokens Studio JSON, Figma Variables export 아무거나 된다. 없으면 코드에서 쓰이는 색을 긁어서 후보를 만들어 줄게.

3. **코드 스캔** — 위 둘 다 없으면 `tokens.py scan <프로젝트루트>` 를 돌린다.
   결과의 `hardcoded`만 후보로 본다. `in_definition_files`는 이미 정본일 가능성이 높다.
   빈도 상위 색을 보여주고 "이 중 브랜드 색이 어느 것인지"를 물어본다.

Tokens Studio JSON을 받으면 `$value` / `$type` 구조를 그대로 읽는다. 원시와 기능이 이미 나뉘어 있으면 그 구분을 존중하고 새로 만들지 않는다.

## STEP 2. 원시 토큰 확정

- 색군 이름은 **색 이름**으로 짓는다 (`coral`, `sky`, `gray`). 역할 이름(`primary`, `brand`)을 원시에 붙이지 않는다.
- **확정값이 하나면** `tokens.py scale <hex> <이름> <단계>`. 기준색이 몇 단계인지 확인한다. 보통 500이지만 아닐 수 있다.
- **확정값이 둘 이상이면 반드시 `tokens.py fill`을 쓴다.** `scale`은 앵커를 하나만 받아서 나머지 확정값과 어긋난다. 브랜드가 500과 700을 함께 고정해 두는 건 흔하다.

  ```bash
  echo '{"500":"#FF8A7A","700":"#E2503C"}' > /tmp/x.json
  python3 tokens.py fill /tmp/x.json coral
  ```

  결과에 `not_monotonic_after`가 있으면 확정값끼리 간격이 어긋난 것이다. 사용자에게 알린다.
- `gamut_clipped`에 뜬 단계는 sRGB를 벗어나 잘렸다. 채도가 무너져 브랜드와 무관한 색이 됐을 수 있으니 눈으로 확인하고 손보정을 권한다. 채도 높은 색의 800~950 구간에서 자주 난다.
- 생성값은 **출발점이다.** 사용자에게 표로 보여주고 확정을 받는다. 손보정한 값이 있으면 그것이 정본이다.
- 확정 후 `tokens.py audit` 으로 사실상 중복인 색을 찾는다. 있으면 통합을 제안한다.

**상태 색을 반드시 함께 묻는다.** `danger`는 필수 토큰인데 브랜드 팔레트에는 없는 경우가 많다. 없으면 이렇게 묻는다.

> 에러·삭제에 쓸 빨강이 팔레트에 없다. 기준색을 정해줄래? 정하기 전이면 브랜드 색을 임시로 빌려 쓰겠지만, "위험"과 "브랜드"가 같은 색 계열이 되는 건 좋지 않아서 나중에 바꾸는 게 좋다.

임시로 빌려 썼으면 그 사실을 `docs/DESIGN_TOKENS.md`와 `docs/log/decision-backlog.md`에 남긴다.

색이 4~6군을 넘어가면 그 자체가 신호다. 정말 다 필요한지 물어본다.

## STEP 3. 체계 결정

`references/naming.md` §2의 감지 규칙을 적용한다. 결정과 근거를 사용자에게 한 줄로 알린다.

> `nativewind` 의존성이 있어서 역할 단계형(체계 A)으로 간다. shadcn/ui를 쓸 수 없는 환경이라 foreground 쌍형의 이점이 없다.

기존 프로젝트에 이미 한쪽 체계가 있으면 감지 규칙보다 그것이 우선이다.

## STEP 4. 기능 토큰 매핑 (라이트)

`references/naming.md` §3 또는 §4의 토큰 목록을 채운다.

- 각 역할에 **어떤 원시를 쓸지 후보를 제시**하고 사용자 확정을 받는다. 역할 매핑은 디자인 의도라 자동 판정이 안 된다.
- 기능 토큰 값은 반드시 원시 참조다. hex를 직접 쓰지 않는다.
- 프로젝트 고유 색군(도메인 색 등)이 있으면 같은 단계 구조로 확장한다.

## STEP 5. 다크 값 도출

`references/naming.md` §5의 규칙을 항목별로 적용한다. 요약하면 이렇다.

- 면은 순서를 뒤집는다. 눌린 면일수록 밝아진다. 순검정을 쓰지 않는다
- 글자는 "배경에 가까울수록 흐리다"를 유지한다. 밝기 방향은 반대가 된다. 순백을 쓰지 않는다
- 브랜드 색은 한두 단계 밝은 원시로 바꾼다
- `on-` 토큰은 처음부터 다시 계산한다. 라이트에서 흰색이었다고 다크에서도 흰색이 아니다

## STEP 6. 대비 검사

`references/naming.md` §3 또는 §4의 **필수 대비 쌍**을 라이트·다크 양쪽에 대해 JSON으로 만들고 `tokens.py check` 를 돌린다.

```json
{ "text on bg (light)":   ["#1C1E1A", "#FFFFFF"],
  "border-strong (light)": ["#7B8074", "#FFFFFF", "ui"] }
```

세 번째 항목이 기준이다. 생략하면 `text`(4.5:1)다. 경계선·아이콘 같은 UI 요소는 `ui`(3:1)를 명시한다. **기준을 안 붙이면 통과한 항목이 미달로 뜨고, 그걸 고치려다 멀쩡한 색을 망친다.**

- `--md`를 붙이면 마크다운 표로 나온다. `docs/DESIGN_TOKENS.md`에 그대로 붙인다
- 미달 항목은 값을 조정하고 다시 돌린다
- 조정해도 브랜드 제약으로 못 넘기면 **그 사실과 사용 제한을 문서에 적는다.** 예: "`text-subtle`은 2.7:1이라 본문에 쓰지 않는다. 플레이스홀더 전용"
- 최종 결과표를 사용자에게 보여준다. 통과한 것도 함께 보여준다

## STEP 7. radius · spacing

`tokens.py scan` 결과의 `radius`·`spacing` 항목을 쓴다. 없으면 이 단계를 건너뛰고 STEP 10에서 그 사실을 보고한다.

- radius: 단계 이름은 `sm/md/lg/xl/full` 또는 프로젝트 기존 규칙. 값이 5개를 넘으면 통합을 제안한다
- spacing: `scan` 결과에서 `off_scale: true`인 값(4의 배수가 아닌 것)을 뽑아 의도인지 물어본다
- 기능 레이어를 억지로 만들지 않는다. radius·spacing은 대개 원시 한 층으로 충분하다

## STEP 8. 파일 생성

`references/naming.md` §6의 형식으로 스택에 맞는 것 **하나만** 만든다.

| 산출물 | 내용 |
| --- | --- |
| 토큰 정의 파일 | Tailwind v4면 CSS `@theme` + `:root`/`.dark`, v3·NativeWind면 `tailwind.config.*` (+ RN 전용은 `theme/`) |
| `docs/DESIGN_TOKENS.md` | 원시 표, 기능 매핑 표(라이트·다크), 대비 검사 결과, 사용 규칙, 미달 항목의 사용 제한 |
| `CLAUDE.md`의 디자인 토큰 섹션 | 요약으로 교체. 상세는 `docs/DESIGN_TOKENS.md` 링크 |

표의 "토큰 정의 파일"은 스택에 따라 파일 수가 다르다. NativeWind는 구조상 세 개(`tailwind.config.js` + CSS + `theme/*`)가 나온다. "하나만"은 체계 하나를 뜻하지 파일 하나가 아니다.

`CLAUDE.md`는 **디자인 토큰 섹션만** 고친다. 다른 섹션은 건드리지 않는다.
`CLAUDE.md`가 아예 없으면 **만들지 않는다.** kickoff 스킬의 일이다. STEP 10에서 "CLAUDE.md가 없어 반영하지 못했다"고 보고한다.
기존 `docs/DESIGN_TOKENS.md`가 있으면 덮어쓰기 전에 물어본다.

다크 전환 방식은 `references/naming.md` §6의 스택별 지시를 따른다. 웹은 `:root:not(.light)`, RN은 선언 순서다.

**배선을 확인한다.** 만든 CSS 파일이 앱 진입점에서 import되지 않으면 토큰이 전부 죽는다. import 구문이 없으면 추가하거나, 범위를 벗어나면 STEP 10에서 명시적으로 알린다. 조용히 넘어가면 사용자는 "스킬이 만든 게 동작하지 않는다"만 보게 된다.

## STEP 9. 하드코딩 감사 리포트

`tokens.py scan` 결과와 확정된 토큰을 대조해 리포트를 낸다. **치환은 하지 않는다.**

| 하드코딩 값 | 위치 | 대응 토큰 후보 | 확신도 |
| --- | --- | --- | --- |
| `#FF8A7A` | `components/Button.tsx:14` | `primary` | 높음 (정확히 일치) |
| `#FF8B7B` | `app/index.tsx:31` | `primary` | 중간 (1 차이, 오타 추정) |

같은 값이라도 의도가 다를 수 있다는 점을 명시한다. 버튼 배경의 `#FF8A7A`와 경고 아이콘의 `#FF8A7A`는 다른 토큰이 되어야 할 수 있다.

`scan` 결과의 `in_docs`도 함께 보고한다. 문서에 복사된 hex는 코드와 어긋나기 가장 쉬운 지점이다.

사용자가 치환을 지시하면 그때 파일 단위로 진행하고, 각 치환 후 검증 명령을 돌린다.

## STEP 10. 보고

- 만든 파일 목록
- 원시 몇 군 몇 단계, 기능 토큰 몇 개
- 대비 검사 결과: 통과 N개, 미달 N개(각각의 처리)
- 손보정이 필요하다고 판단한 생성값
- 하드코딩 감사 요약: 총 N건, 자동 대응 가능 N건, 판단 필요 N건
- 건너뛴 것 (radius·spacing 없었음 등)

커밋 제안은 두 개로 나눈다.

```
feat: 디자인 토큰 2층 구조 정의
docs: 디자인 토큰 문서 추가
```

실행 여부는 사용자에게 묻는다.

## 하지 말 것

- `references/naming.md`를 읽기 전에 토큰 이름 짓기
- 스크립트 없이 눈대중으로 스케일·대비 판정
- 원시 토큰에 역할 이름 붙이기 (`primary-500`)
- 기능 토큰에 hex 직접 쓰기
- 하드코딩 색을 확인 없이 일괄 치환
- 대비 미달을 보고에서 빼기
- 다크 값을 단순 반전(255-v)으로 만들기
- 다크 배경에 순검정, 다크 본문에 순백
- `CLAUDE.md`의 디자인 토큰 외 섹션 수정
- 확정값이 둘 이상인데 `fill` 대신 `scale`을 써서 확정값을 덮어쓰기
- `check`에서 UI 요소 쌍에 기준을 안 붙여 오탐을 진짜 미달로 취급
- `CLAUDE.md`가 없는데 새로 만들기
- CSS 파일을 만들고 import 배선을 확인하지 않기
- 자동 커밋
